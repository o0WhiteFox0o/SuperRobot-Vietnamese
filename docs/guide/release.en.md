# Release build

There are two download files for public release: the application body (original screen), and a separately downloadable HD image package.
Both are built from a single commit by `tools/release/build_release.py` and are not affected by uncommitted changes from other sessions in the shared workspace.
The script is only responsible for building, not publishing; publishing is another manual step.

## Build once

```sh
.venv/bin/python tools/release/build_release.py --commit HEAD --version 0.4.2
```

- The output directory defaults to `build/release/<版本>-<短提交号>`, and refuses to be overwritten if it already exists. You can use `--output` to specify, and `--keep-source` to retain the checkout directory and compiled products.
- Prerequisite: The main workspace already has `build/recomp/{upstream,tool-build,cpu-scan}` generated by `rom.z64`, `assets/`, `make all`, and
[macOS dependencies](../native/macos-release.md)(`build/macos-deps/14.0-arm64/prefix`).

Steps:

1. Use `git worktree add --detach` to check out the commit to `输出目录/src`.
2. Link the ROM in; `hd-ai`, `fonts`, `models` in `assets/` are cloned using copy-on-write (art compilation does not accept paths pointing outside the checkout directory), and the rest are linked.
3. Clone the upstream source code and compiled tools of the fixed tool chain, restore RT64 (including submodules) to the locked original state (uncommitted RT64 changes from other sessions in the main workspace will not mix in, and will not be rejected by `prepare_rt64.py`), and then regenerate only the submitted code: CPU code, RT64 patches, front-end adaptation layer, audio microcode, fonts.
4. Run all Python tests.
5. Compile from scratch on macOS 14/arm64 and create the application package.
6. Rebuild the ship model package and 5600 mark package, make HD package, and attach `tools/release/hd-notice.txt` (installation method, AI generation source, unofficial statement).
7. The two files are compressed with `ditto --norsrc --noextattr`: without `__MACOSX` and extended attributes such as isolation and source, they are still valid after decompression by applying the signature.
8. Write out `release.json` (commit, version, size of two files and SHA-256, `hd.json` for HD package, release command)
and the release notes filled in as per `tools/release/release-notes.md`.

The entire process takes about 3 minutes natively: less than a minute to compile 942 steps from scratch, and about 40 seconds to test.

### Internal beta version (with ROM and HD, no external distribution)

2026-09-29 Users want an internal beta version with ROM installed. First add `--keep-source` to build as above, then put the compiled program, `pack/hd` and ROM into the application:

```sh
cd build/release/<版本>-<提交>/src
PYTHONPATH=src:tools ../../../../.venv/bin/python tools/release/package_macos.py \
  --binary build/recomp/macos14-app-build/srw64-gfx-host --output "../app-internal/Marchwind64.app" \
  --version <版本> --minimum-macos 14.0 --search-dir ../../../macos-deps/14.0-arm64/prefix/lib \
  --runtime-library ../../../macos-deps/14.0-arm64/prefix/lib/libSDL3.dylib \
  --fonts build/fonts --dialogue content/dialogue --hd ../pack/hd --rom rom.z64
```

- `--rom` First press `config/recomp/rom-variants.json` to check SHA-256, only the Japanese version Rev 0 will be accepted; ROM is put into `Contents/Resources/rom.z64`, `Distribution.txt` The first line states that it is an internal test version, contains ROM, and is not allowed to be exported.
- The ROM packaged at startup (`src/host/host.cpp`) replaces the ROM selection box that pops up for the first time: this Mac still uses the remembered one when remembering other ROMs; hold down Option or `--choose-rom` and the selection box still pops up.
- This application does not import `release.json`, nor is it compressed into a distribution file; `build_release.py` itself never comes with a ROM.

### Attach packages for other platforms

Linux packages and Windows packages are built by GitHub Actions' `build` workflow (`.github/workflows/build.yml`; push main, push `v*` tag, or trigger manually):
On Ubuntu, the game code is generated from the ROM of the private repository `dyzz/srw64-ci-inputs`, encrypted and handed over to Windows (clang-cl) and Linux (with `tools/release/linux/build.sh`
The same Ubuntu 22.04 container) two tasks; the finished products are also encrypted and uploaded (anyone can download the products in the public warehouse), and use local `~/.config/srw64/ci-artifact-key` to unlock:

```sh
gh run download <运行号> --repo dyzz/srw64-recomp -n Marchwind64-linux-x64-encrypted
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass file:$HOME/.config/srw64/ci-artifact-key -in Marchwind64-linux-x64.tar.gz.enc -out Marchwind64-linux-x64.tar.gz
```

The Windows package is also downloaded as `Marchwind64-windows-x64-encrypted`. After unzipping, it will be the `Marchwind64-windows-x64` folder, compress it into a zip and attach it.
Download the Android package `SRW64-android-arm64-encrypted`, and after unzipping it is the APK (CI is signed with the release key in the warehouse, which can overwrite and install the old version and keep the archive);
`android:versionName` and `versionCode` are in `tools/release/android/app/AndroidManifest.xml`, which will be changed together with the root directory `CMakeLists.txt` when releasing the version.
(versionCode = major version × 10000 + minor version × 100 + revision number, 0.4.0 is 400, and can only be made larger; `tests/test_release_version.py` Check that the three places are consistent). Steam cover image is `tools/release/linux/steam-art/` in the warehouse
(`steam_art.py` is generated from the HD title image. If you change the title image, regenerate and submit it). The Linux package built by CI also has a cover.

Linux packages can still be built natively (`tools/release/linux/build.sh` or `build_linux.py` in a clean checkout), Windows packages are only built by Actions,
Pass `--attach` to the same `build_release.py` and put it into the same release as the Mac package and HD package:

```sh
.venv/bin/python tools/release/build_release.py --commit HEAD --version 0.4.2 \
  --attach linux=build/deck/<提交>/src/build/linux-x64/Marchwind64-SteamDeck-0.4.2-<日期>-<提交>.tar.gz \
  --attach windows=build/windows/<提交>/Marchwind64-0.4.2-windows-x64.zip \
  --attach android=build/android/<提交>/SRW64-android-arm64-<提交>.apk
```

The attachments are renamed `Marchwind64-<版本>-linux-x64.tar.gz`, `Marchwind64-<版本>-windows-x64.zip`, `Marchwind64-<版本>-android-arm64.apk`, the download table, the three platform installation locations of the HD package, the check value and
The release commands of `release.json` are generated according to the attached package. All three platforms share the same HD package; it can only be built natively (the assets are not put into the warehouse), so it is always generated from this step.
Attached packages must come from the same submission: HD packages only match the same version of the application.

## Publish

After confirming `release-notes.md` and the two files, execute the `gh release create` command noted in `release.json` in `publish`.
Tags are pinned to build-time commits with `--target`. GitHub has a 2 GB limit for a single attachment, and both files are significantly smaller than that.

## Contents and constraints of HD packages

- Art comes from native assets referenced by `content/art/stage1-hd.json`; ships and token packs are rebuilt from the scripts in the commit, excluding ROM bytes.
- The AI graphs in the package do not write AIGC metadata, but are only declared in text in the package description and release notes.
- The public HD package is a complete HD folder, which is the same as the one for personal use (2026-09-28 user-defined): the body rendering, map body icon and
HD tactical maps (including color-coded images) are included in the package, and the NOTICE and release notes indicate that they are pixel-enlarged from the original. The previous public package deleted the tactical map and icon (`ROM_DERIVED*`) and has been cancelled.
- The BANPRESTO logo and GAME OVER in the HD window border and title image are generated by the game from the player's own ROM at runtime (99d5cb2, 7b0d7f5),
They are not in the art list.
- The player puts the extracted `hd` folder into the user directory (`~/Library/Application Support/SRW64Recomp/hd` for macOS),
Or put it in the folder where the game is located (next to `Marchwind64.app`, `marchwind64.sh`, `Marchwind64.exe`, `beside_game`),
The launcher starts in HD. Search order: User directory → Next to the game → Comes with the application (`Contents/Resources/hd`);
If the folder is incomplete or the version is incorrect, an error will be reported and the original version (`src/native/app/launch.cpp`) will not be quietly returned. On macOS that have not been moved in Finder
The downloaded application will be moved to a read-only copy by the system (App Translocation). At this time, the `hd` next to it cannot be seen; Android does not have a game folder and only recognizes the user directory.
- HD packages only come with apps of the same version. The schema or HD data format of `hd.json` has changed, and new applications and new HD packages must be sent at the same time.
- Volume (`tools/release/compress_hd.py`, 2026-09-28): The entire image is saved in JPEG quality 92, 4:2:0, and if it is transparent, save a grayscale and transparent PNG.
The body rendering is reduced from 8x to 6x ROM pixels, and the long side does not exceed 1024 px; the pre-war confirmation page only displays a maximum of about 830 px (density 2) or 980 px (density 3).
The avatar remains at 768 px and the tactical map remains at 4x as they are not large enough in full screen. RT64 textures can only be PNG or DDS,
So only remove the transparent channel from the opaque ones; BC7 will enlarge the close-up view of the world map into a blocky shape, so it is not used. Result: Full HD down from 708 MB to 409 MB (~400 MB after zip),
The public package is now the same; sampled PSNR is 44 for portraits, 42 for avatars, and 41 dB for maps.
- **Handheld version HD package: studied, not done yet** (2026-09-29 user: "Leave it for research, it will be full HD for the time being"). The idea is to provide a low-resolution package for 1280×800 handheld consoles such as Steam Deck, while the desktop remains as it is.
Based on the class-by-class sampling and heavy compression estimation of the 0.3.0 HD package (385 MB zip), it can only save about 30%, to about 265 MB:

| Part | Now | Handheld version estimate | Description |
| --- | --- | --- | --- |
| Tactical map | 219 MB | About 140 MB | Originally only 4 times the original version, it is displayed on the Deck 3.33 times. The reduction in size saves little, mainly relying on JPEG 92→85; the color map is about 39 MB and cannot be moved (nearest neighbor is used for zooming, and linear interpolation makes it larger) |
| World map (RT64 512² texture) | 83 MB | 83 MB | The close-up view on the Deck requires 10–17x, 8x is not enough, and cannot be reduced |
| Avatar | 38 MB | About 13 MB | 768→384 px; Deck dialogue avatar is about 320 px high |
| Three-dimensional rendering of the aircraft body | 26 MB | About 14 MB | 576→384 px; Deck pre-war page maximum about 300 px |
| Background | 6 MB | About 3 MB | 1920×1440→1280×960 |
| Others | 13 MB | 13 MB | Plots, models, icons |

Cost: The handheld version is significantly weaker when the Deck is connected to a TV or monitor (the tactical map is about 4.5 times more expensive at 1080p); one more package to build, test, and write instructions for.
If you really want to do it, you just need to add a target gear (maximum size and JPEG quality) to `compress_hd.py`. You don’t need to change the loading side, which takes about half a day’s work.
