# Widescreen: Based on Steam Deck 16:10, 4:3–16:9 varies with screen

2026-09-28 The user decided to use Steam Deck’s 1280×800 (16:10) as the resolution benchmark: the battlefield (tactical map) needs to truly expand the field of view, and the interface and field are also adjusted accordingly. 2026-09-29 Added: It needs to be adapted to 16:9, covering most nostalgic handheld consoles, and the special effects must be correct in various resolutions. Therefore, the screen width is not fixed at 384, but varies between 4:3 and 16:9 depending on the screen. 16:10 is the benchmark for design and acceptance. §5 and above are solutions derived from static analysis; the address and line number are based on main (3d3cff6) on 2026-09-28. The superior plan can be found in [Three Platform Transplantation](three-platform-port.md), and the original widescreen vision can be found in [Native Enhancement Planning](native-enhancements-plan.md) §5 (W1/W2).

## 1. Current situation

- RT64 set to `AspectRatio::Original` (`src/host/graphics.cpp:368`), rendering 1× native resolution. The 320×240 screen is a centered 1067×800 in 1280×800, with approximately 107 px black borders on the left and right sides, and a vertical magnification of 3.33 times (not an integer). Linux smoke screenshot (`build/linux-x64/smoke/s1-*.png`) is just that.
- 107 px black border is exactly 32 original pixels. Screen width W = 240 × screen aspect ratio (original pixels), original 320 centered:

| Screen | Example | W | Extra on each side |
  | --- | --- | --- | --- |
| 4:3 | 640×480, 960×720 | 320 | 0 |
| 16:10 | Steam Deck 1280×800 | 384 | 32 |
| 5:3 | 800×480 | 400 | 40 |
| 16:9 | 1280×720, 1920×1080 | 426.7 | 53.3 |
| Wider than 16:9 | 2560×1080 | 426.7 (leave black on both sides) | 53.3 |

- The default window is 960×720 (`graphics.cpp:571`), and the reference size for interface density is also 960×720 (`src/native/ui/frontend.cpp``sync()`); the default interface size of Deck is Largest, about 864×540 dp.

## 2. Mechanism: RT64 renders according to screen width + extended instructions, does not change the frame buffer

Two paths have been compared:

- **A (adopted)**: RT64 `aspectRatio=Manual`, `aspectTarget=W/240`, `extAspectRatio=Expand`. RT64 renders a W-wide target as `resolutionScale.x×W/320`, with the window exactly full (384, 1.2x at 16:10). The following uses 384 as an example. The game still thinks the screen is 320×240; by default its rectangle (`G_EX_ORIGIN_NONE`) is unstretched and centered at 32..352, which means it looks the same as it does now when doing nothing. Things that need to be widened can be selectively released by the host by inserting extension instructions in the display list:
- `gEXEnable`: Sent every frame, each RT64 workload will clear the extended status (`rt64_state.cpp:1833`).
- `gEXSetScissor(LEFT, RIGHT, 0,0,0,240)`: Put the crop to 0..384.
- `gEXSetRectAlign(LEFT, LEFT, …)`: The rectangular coordinates are directly interpreted as 0..384 (the original TEXRECT is unsigned 10.2, and negative x cannot be written, so the game must be typeset in the coordinates of 0..384 instead of −32..352).
- `gEXSetRectAspect(ADJUST)`, `gEXSetViewportAlign(CENTER)`: Used to maintain 4:3 scenes to prevent the background from filling the width and the 3D viewport from being widened.
- **B (not used)**: Change the game frame buffer to 384 width (`0x8010F5C0` screen width, VI mode table `0x80178A10`, buffer address table `0x800C6870`). RT64 will faithfully display 16:10, but each color/depth buffer increases from 0x25800 to 0x2D000 bytes, which requires memory rearrangement, and all images change at the same time, which is risky.

"Keep 4:3 by default" does not need to be written into the game's display list: the host directly sets the RT64 status in `send_dl` (`src/host/graphics.cpp`) before each submission - enable extended instructions (opcode 0x64), rectangle `ADJUST`, viewport `CENTER` - is equivalent to putting these three instructions at the beginning of the list, and does not depend on which path the game takes to build the list (RT64 will clear it for each workload and `rsp->reset()`, so it is set every time). Only scenes that need to be relaxed need to insert instructions into the list.

The position of the inserted instruction: the existing renderer package (`src/host/game_hooks.cpp`, such as the map `800945D4`) calls the original function to write the command to `*cursor`, advances the cursor, and then writes the reset command after the call. The current host only does in-place rewriting (G_NOOP tag), and no additional commands have been added. This is new infrastructure. The common preamble of each frame can be hung on `8008AD40` called by frame display list construction `8008AE90` (need to add `NATIVE_HOOKS`). The display list buffer is 0x24000 bytes per frame, and there is no margin left.

The scale only changes with the window and does not switch according to the scene: RT64 Although each workload rereads the configuration, the switching will be offset by about one frame; to keep the 4:3 scene, just use `ADJUST`+viewport centering. The setting is "Screen Ratio: Auto/4:3 (Original)", and it returns to `Original` at 4:3.

## 3. The host drawing layer should be changed accordingly.

Two types of native drawing layers (`src/host/`):

- **Present hook layer** (dialogue bar and resume, shared RmlUi interface, name page mask) calculates the screen rectangle by itself based on window pixels. To replace "4:3 screen" with "W wide screen + middle 4:3 column": `u=min(窗宽/W,窗高/240)`, add (W−320)/2 to the original 320 coordinates.
- **RT64 scene inner layer**: `fbWidth` in `NativeClip(pixel, fbWidth)` is logic 320.
- `native_marker.cpp:340`, `native_sprite.cpp` Quad paths have been correctly centered or widened using RT64's `screenScale/screenOffset`.
- `native_sprite.cpp` text rectangle (`HdSpriteVS.hlsl`), `native_map.cpp:271` (deliberately set to unit conversion), `native_portrait.cpp:163`, `native_background.cpp:149` are mapped directly by 320. After turning on 1.6, they will be horizontally widened 1.2 times and cropped. Give them a "centered (+32)/left-aligned wide screen" mapping parameter, consistent with the scene's `RectAlign`.

## 5. Tactical map expansion

The mapper `800945D4` (wrapped as `srw64_original_map_draw`) has one 16×16 CI textured rectangle per cell, and does not cycle through rows and columns, but culls cell by cell. The coordinates need to be changed to 0..W, so the game's own "screen" needs to be widened to W. The new value in the table below is written as W=384; the actual value should be taken according to the W value at runtime (when W=320, it is equal to the original value). The 426.7 of 16:9 is rounded to 426 for game logic, and the excess is less than 1 pixel and is left black. Change points (original value → 16:10 value):

| Position | Function | Change |
| --- | --- | --- |
| `800945D4` @`80094A94` | Right culling `x+16 < 0x149` | → `0x189` |
| `801FFCB0` (about 48 calls) | Center by point: scrollX = clamp(152−px, 320−W, 0) | 152→184, 320→384; center when map width <384 (see below) |
| `801FFADC` | Follow cursor every frame: scroll when x>272 or <32 | 272→336 |
| `801FFE34` | "Click on the screen" [32,288]: `0x101` | → `0x141` |
| `801FFE78` | Center box [96,224]: `0x81` | → `0xA1` (optional) |
| `801E4760` @`801E4888`, `801E49A4` @`801E4B20`, `801E4D10` @`801E4E5C/70` | Move/Attack range full frame draw border `0x138` | → `0x178`; Edge 8 px clipping of fragment path not read yet |
| `801E44BC` | Grid `0x140` (three places), `0xF0` | → `0x180` |
| `801CABAC` | The terrain panel follows the left and right gripping of the cursor 189/156 | → 221/220, or maintain |
| Script scrolling 3D35/3D34/3D36 screen shake, `801C8E20` and other inline re-centering | The gripping range is unknown | Read one by one |

The host already has functions that depend on these boundaries and must be changed together: `enemy_cycle.cpp:89` and `move_jump.cpp:160` use `801FFE34`.

- **Method to change constants**: Now there are only whole function wrappers (`NATIVE_HOOKS` of `tools/recomp/toolchain/generate_cpu.py`). It is recommended to add an "immediate number patch" table to `generate_cpu.py`: replace the constant with `srw64_wide(旧值, 新值)` according to the function and instruction address, set the value according to the screen ratio during runtime, and verify the original value. If it is not found, the generation will fail. This way the behavior in 4:3 mode is byte-for-byte consistent with the original. Small functions (`801FFCB0`, `801FFADC`, `801FFE34`) can also be rewritten directly in the host.
- **Narrow Maps**: Only 11 maps are exactly 320×240 (34, 65, 66, 70, 73, 74, 81, 116, 117, 119, 157), the rest are as narrow as 432, which is wider than 427 in 16:9. The clamping interval of the narrow map will be inverted, `801FFCB0` will pin it to the left and leave W−320 on the right; to center it (scroll=(W−320)/2), draw dark borders on the areas outside the map on both sides.
- **HD map layer**: `native_map.cpp` Originally, the uv is taken from the entire map basemap according to the camera, and the bounding box automatically becomes larger with the elimination and relaxation; the mapping needs to be changed to 384 width, and the uv is sandwiched within the map (narrow maps cannot be stretched).
- **HUD** on the map (unit window, command menu, stage banner) statically not finding coordinates. If the game is still arranged according to 320, it will be 32 px to the left under `LEFT` alignment; either find the coordinates one by one and add 32, or only enable `LEFT` for the map, unit, range, and cursor, and the HUD will remain centered by default. The latter requires less changes, so do it first.
- Unit icon `801E21F8/801E26C0` This function does not eliminate, and it is unknown whether the caller eliminates it; the damage number `80209900` has no screen boundary constant.
