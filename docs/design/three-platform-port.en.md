# Three-platform porting plan: Windows/Linux/macOS

2026-09-24. Continues [P0 Release Plan](cross-platform-release-plan.md) and [P1 Native Import](native-rom-importer.md).
This page replaces the order and thresholds of P2–P4 in P0; P0's goals, player flow, authorization boundaries, and "no deletion of features to declare completion" constraints are still valid.
The conclusion comes from a static audit of the host C++, build toolchain and upstream RT64/plume/N64ModernRuntime that day, **not actually built or run on Windows/Linux**.

## Target platform

| Platform | Graphics Backend | Compiler | First Packages | Acceptance Machine |
| --- | --- | --- | --- | --- |
| macOS arm64 | Metal (via plume) | Apple clang | `.app` zip | Current development machine |
| Linux x64 (with Steam Deck) | Vulkan (SDL Vulkan window) | clang | tar.gz, glibc 2.35 baseline | Linux x64 machine or Deck |
| Windows x64 | D3D12 default, failback Vulkan | clang-cl + Ninja | zip | Windows x64 machines |

- **Backend selection. ** Follow RT64's `GraphicsAPI::Automatic`, do not write the selection logic yourself. Its rules are: use D3D12 for Windows, use Vulkan under Wine or when encountering known bad drivers; use Metal for Apple; use Vulkan (`rt64_user_configuration.cpp:142`, `rt64_application.cpp:133-289`) for other platforms.
- **Self-drawn GPU code. ** All use plume’s common interface (`RenderDevice`/`RenderCommandList`). Shaders are written in HLSL, precompiled into SPIR-V, DXIL (Windows only) and MSL when building, and embedded in the program, as per `cmake/PixelCompositor.cmake`. MSL source code is no longer compiled at runtime.
- **macOS has also switched to the same implementation. ** Two sets of HD layer codes are not retained.
- **Compiler. ** clang-cl is consistent with Windows CI of RT64 and Zelda64Recomp; the C generated by recompiling is already compatible with MSVC, clang and gcc in `recomp.h`.

## Current situation

**ALREADY PORTABLE:**

- **Upstream:** RT64 is programmable with three backends: D3D12, Vulkan, and Metal. N64ModernRuntime is available on Windows/Linux.
- **Recompile output:** The generated `funcs_*.c` is platform independent, contains no host path, and has no OS conditions.
- **Dialogue and interface:** Use `PixelCompositor` for dialogue and FreeType/HarfBuzz/ICU for text. The RmlUi interface already has three branches: SPIR-V/DXIL/MSL.
- **Input & Audio:** SDL gamepad and keyboard input (`graphics.cpp:520-620`), SDL audio.
- **Application layer:** `src/native/app` has been separated into Windows and POSIX paths, covering file locks, atomic replacement, user directories and executable file paths.
- **Hooks:** RT64's native-mesh hooks and present hooks are backend-agnostic. This repository only uses the plume type for hook patches for RT64.

**Blocking items, ranked by workload:**

1. **Five HD layers call Metal directly. ** Involving `native_marker/map/portrait/background/sprite.cpp`: about 250 lines of MSL, about 380 lines of Metal API. They directly take the `plume::Metal*` underlying object, end the RT64 encoder themselves, open a new rendering pass, use `setVertexBytes` to stuff constants (maximum 4 KiB), use `replaceRegion` to upload textures, and finish with Metal's completion callback. The remaining approximately 60% is logic such as RDRAM recognition and JSON, which can be directly reused.
2. **Three gaps in plume:**
- There is no texture→buffer copy on Vulkan and Metal, and screenshot reading cannot be done.
- The Vulkan swap chain image does not have the `TRANSFER_SRC` flag and cannot be used as a copy source.
- No GPU completion callback: `graphics.cpp:94,161` has no corresponding interface to `addCompletedHandler` of `dialogue_plume.cpp:51,59`.
3. **Compiler and CMake:**
- Non-Apple platforms directly `FATAL_ERROR` (`src/host/CMakeLists.txt:59`).
- Unconditional use of `-framework`, `-fblocks`, OBJCXX; `-include stdlib.h` will fail to compile under clang-cl.
- `flockfile` (`script_trace.hpp:49`) via `state_probe.hpp` is included by almost all host source files and will directly block Windows compilation.
- `path::c_str()` is `wchar_t` on Windows, passed to `stbi_*` or `%s` at about 12 places.
- Missing `/utf-8` and `M_PI` definitions.
4. **Python Toolchain:**
- `venv/bin/python` paths and executable file names without `.exe` are hard-coded.
- `bootstrap.py:55` and `run_host_probe.py:206` force clang + Ninja.
- At about 264 locations `read_text`/`write_text` no encoding is specified. Among them, `build_import_spec.py` called during CMake configuration will write the interface copy into garbled characters under Windows local encoding.
- `fcntl` is imported at the top level of the module.
5. **Debugging interface:** uses AF_UNIX socket (`debug_server.cpp:297`, `session.py:48`). Mini-levels are compiled using POSIX quotes `std::system` (`mini_stage.hpp:274`). MCP's stdio does not have UTF-8 fixed.
6. **Window and platform interface:**
- Window: `SDL_WINDOW_METAL` + Cocoa handle (`graphics.cpp:466-480`).
- ROM selection and error boxes use AppKit (`macos/desktop_macos.mm`). Menu bar `app_menu.mm` has empty implementations and RmlUi alternative paths on other platforms.
7. **Dependencies and build environment:**
- Linux precompiled `dxc-linux` requires glibc 2.34.
- Debian 11/Steam Runtime sniper's ICU (67) and HarfBuzz (2.7.4) are below requirements (≥70, ≥2.8).
- SDL2 2.26.3 that comes with RT64 on Windows conflicts with the host `find_package(SDL2)`.

## Stage

### X0 Portable Base (do it on Mac, same behavior)

No new machinery is required. The goal is to have code that compiles on all three platforms, but behaves exactly the same on Mac.

- **CMake:**
- Replace "Metal host" with `SRW64_ENABLE_RT64`.
- Apple-specific source files and linkage options are included in `if(APPLE)`, `-fblocks` is only for files that still reference Metal header files.
- `-include` is written as `-include` or `/FI` depending on the compiler; Windows adds `/utf-8`, `NOMINMAX`, `_USE_MATH_DEFINES`.
- Add `-msse4.1` to RSP vector codes on x64.
- Added `CMakePresets.json`, divided into three sets: `macos-arm64`, `linux-x64`, `windows-x64-clangcl`. The compiler is no longer hard-coded in scripts.
- **Source code:**
- `flockfile` replaced by `std::mutex`, or `_lock_file` on Windows.
- The path is uniformly changed to `path.u8string()`, and then passed to `stbi_*` through a small tool function.
- Mini-level compilation is changed to directly start the child process with the argv list.
- **Debug Interface:** Changed to native loopback TCP: port is temporarily allocated, token is written into existing `debug.json`. `srw64ctl`, MCP and tests are adjusted together. The actual machine acceptance of the three platforms must be driven by it, so it is placed in the first batch. (Completed on 2026-10-06, see `src/host/debug_transport.cpp` and [Debug Interface · Connection Method](../guide/debug-interface.md#连接方式); Windows real machine has not been verified.)
- **Python:**
- Makefile and CMake's `execute_process` sets `PYTHONUTF8=1`, and tool functions gradually add `encoding="utf-8"`.
- `fcntl` is replaced by the compatibility layer (Windows uses `msvcrt.locking`).
- The venv path and `.exe` suffix are handled by a common helper function.
- `generate_cpu.py` Fixed `newline="\n"` when writing files to ensure that the summary of the generated product is consistent across platforms.
- **Acceptance:**
- `make`, `make recomp-native-check` and existing check scripts all pass on Mac.
- Ability to compile at least CPU-only `srw64-host` and root CMake tests in Linux containers. Docker is installed on this machine but is not currently started.

### X1 graphics layer is changed to plume (completed and accepted on Mac)

**2026-09-25 Progress:**

- **Auxiliary layers:** `src/host/native_gpu.{hpp,cpp}`; shaders are HLSL under `src/host/shaders/`, compiled from `cmake/NativeGpu.cmake` into SPIR-V, MSL (via RT64's conversion tools, `flip_vert_y` offset `-fvk-invert-y`) and DXIL.
- **Data for each draw:** Written into a shared `StructuredBuffer<float4>` ring buffer, and the subscript is passed to the shader via push constant. RT64 waits for the GPU to complete after each workload is submitted (`rt64_workload_queue.cpp:843-844`), so it is safe to reuse the ring slot; this also avoids the lower limit of Vulkan's 128-byte push constant.
- **RT64 Patch:** `NativeMeshDraw` takes the color format, depth format and number of samples of the scene target (`native_model_hook_patches.py`).
- **Five layers have been transplanted (2026-09-25):** Map, background, markers (golden markers, halos, ship and landmark models, tracks, nameplates), scene sprites (title cards, plot text images, original UI text), and the entire avatar. The Linux null implementation has been removed and all layers compile on all three platforms.
- **Layer-by-layer before and after comparison on Mac** (same scene, before Metal porting and after Plume porting):
- Inter-scene background: The maximum difference between HD scenes in the same archive is 1 level.
- Tags: `ra-cailum`, `worldmap-libra` The mini-levels are drawn the same number of times, and the screenshots only differ in animation phase (driven by host time).
- Sprite: `act` title card, `ending` ending page are consistent frame by frame or only differ in transition frame.
- Avatar: `scene8` Press Z to advance the dialogue. The HD avatars of Byoti, Jia'er, Wan Zhang, and Garrison are the same.
- The tactical map is only enabled when `SRW64_HD_MAPS` is set, and is not compared separately.
- **Vulkan path (MoltenVK):** `SRW64_GRAPHICS_API=vulkan` (for testing only) Let RT64 on Mac use the Vulkan backend; for this reason, the SPIR-V shader is embedded in all platforms, `graphics.cpp`, `dialogue_plume.cpp` Select Metal-specific paths by actual backend instead of by platform. The same four scenes plus inter-scene scenes: Vulkan and Metal screenshots are consistent, including dialogue boxes and RmlUi pages.
- **Vulkan/D3D12 screenshot read back:** plume's Vulkan backend adds texture → buffer copy, swap chain image adds `TRANSFER_SRC`, RT64 provides the current swap chain texture (`GetRenderHookSwapChainTexture`) to the drawing hook. Screenshots of the debug interface are now available on Vulkan.
- **RT64 issues discovered and fixed on Linux:**
- Native draw marked with a textured rectangle has no triangles, old patches read `faceIndices` out of bounds. It happens not to crash on Mac, but segfaults on Linux; now it takes 0 when out of bounds.
- When there is no D-Bus session bus, RT64's file dialog library fails to initialize, but still calls `NFD_Quit` when exiting and aborts; now it is only called when initialization is successful.
- **Crash call stack:** The Linux host prints the call stack to stderr (`host.cpp`) when it receives a signal such as SIGSEGV, parsed with an unstriped build and `addr2line`.
- **Before and after comparison method:** `srw64ctl launch --binary PATH` (i.e. `run_host_probe.py --binary`) runs the specified program. The pre-migration program is built from a worktree: the current source code plus the HEAD version of the layer to be ported.

This is the biggest piece, and the whole process can be verified on Mac: plume’s Metal backend is now the bottom layer.

- **Shared auxiliary layer** (tentative name `native_gpu`):
- Pipeline cache keys: color format, depth format, number of samples, depth mode, blending mode. plume bakes the depth and mix state into the pipeline, so both are keyed.
- Per-frame rotation constant buffer, instead of `set*Bytes`. 192 B of uniforms exceeds Vulkan's guaranteed 128 B push constant lower limit; 2–4 KiB of palette and quad data would have been buffered.
- Texture upload buffer + `copyTextureRegion` + barrier; mipmap generated on CPU.
- Delayed release of resources by fence, replacing the current "release after 20 seconds of inactivity" assumption.
- **Transplantation sequence** (from simple to complex, each step is accepted separately): map → background → portrait → sprite → marker. The marker has five pipelines, four depth states, and a 4 MiB track buffer.
- **Drawing position:** Draw directly in the RT64 bound frame buffer, without ending the encoder and opening a new rendering pass. After the hook returns, RT64 rebinds the pipeline layout, descriptor set, and viewport (`rt64_framebuffer_renderer.cpp:477-488`), but does not reset the framebuffer, so the hook cannot replace it.
- **`graphics.cpp`:**
- Name page occlusion changed to `setFramebuffer` + `clearColor`.
- Screenshot readback and framebuffer format query are changed to plume.
- Changed `GraphicsAPI::Metal` to `Automatic` in two places.
- **Dialogue:** `dialogue_plume.cpp` is moved out of `macos/`, the `metal_*` entry is renamed, and the shader format is taken from `getCapabilities().shaderFormat`.
- **RT64/plume patch** (follow the whitelist string replacement of `prepare_rt64.py`, do not fork):
- Vulkan and Metal patch texture→buffer copy.
- Vulkan swap chain image plus `TRANSFER_SRC`.
- `rt64_present_queue.cpp` calls a "rendering completion" hook after `presentGraphicsWorker->wait()` with the workload id to replace the Metal completion callback. It still must satisfy the constraints of P0: the interface only corresponds to the workload being presented, and cannot read the "latest RDRAM" and overwrite old frames.
- **Acceptance:**
- Use the fixed-point screenshot method in [Ship Model](../native/native-ship-model.md) (a mini-level with determined timing, one screenshot every 50 VIs), compare the HD images before and after transplantation, and check layer by layer.
- The name page is blocked without flickering; screenshots and debugging interface screenshots are normal; F6/F7 and zoom are normal.
- Optional: This machine has Homebrew's MoltenVK 1.4.1 installed. If the RT64 Vulkan backend can run on Mac, the SPIR-V path can be tested before getting a Linux machine. **This has not been verified. **

### X2 Linux x64 with Steam Deck

2026-09-25 Adjust the order: Users need to play on Steam Deck first, so X2 starts before X1, in two steps:

- **D1 original screen version** (the code has been written, please see [Linux Build](../guide/linux-build.md) for construction and instructions):
- The five HD layers are first replaced with empty implementations on non-Apple platforms and handed over to RT64 to draw according to the original display list (deleted after X1 is completed).
- Windowing, backend selection, GPU completion notification (RT64 patch `RenderHookPresented`), name page occlusion, dialogue compositing are all backend independent.
- Debug screenshots returning errors on Vulkan at the time (X1 was padded with readback).
- Added controller → key bridging to the shared interface: Native pages other than the battle page originally only recognized the keyboard. Now, pressing the controller will convert it to the same set of keys (`frontend.cpp` and `pad_keys`). Deck can also operate the field, title, archive and name page using only the controller.
- **D2 HD version** (code completed on 2026-09-25): All five HD layers have been changed to plume, the empty implementation has been deleted, Linux and Mac share the same set of implementations; the Vulkan path has been compared with MoltenVK and Metal on Mac (see X1). Using the HD material package on Deck is the complete HD version, which is still to be confirmed by the actual Deck machine.

Here's the complete list of X2:

- **Window:** `SDL_WINDOW_VULKAN`, hand `SDL_Window*` to RT64/ultramodern; `RT64_SDL_WINDOW_VULKAN` is already open.
- **Dependencies:**
- Generalize `config/recomp/macos-dependencies.json` into dependency locks grouped by platform, using the same batch of SDL, FreeType, HarfBuzz, ICU source packages and SHA-256.
- Link statically on Linux, or load it next to the program using `$ORIGIN` rpath. Does not rely on the system or Steam Runtime's own ICU.
- **Build environment:** Using Ubuntu 22.04 x64 container (glibc 2.35), meeting the precompiled `dxc-linux` requirement. CMake and Python 3.11 are individually fixed.
- SteamOS's glibc is newer than 2.35, and the generated package can be run directly in the "non-Steam game" mode.
- Steam Runtime sniper (glibc 2.31) left for later: requires coding DXC from source, or feeding precompiled shaders from elsewhere.
- **Steam Deck:**
- Full screen 1280×800.
- All RmlUi pages can be operated using only a controller; see [Steam Deck Keys and Button Icons](steam-deck-controls.md) for key positions, setting entries and button icons.
- There is no desktop dialog box in game mode, so the ROM selection and error prompts are changed to RmlUi pages, consistent with the policy of "only using RmlUi for the interface". It is recommended that macOS also use this page instead, and then delete `desktop_macos.mm`.
- Use the font packaged with HarmonyOS; add the `noto-cjk/` path of Arch with the backup font list of `frontend.cpp:1449`.
- **Acceptance:** Run the Linux desktop and Deck game modes once each, and only use the controller on the Deck:
- Opening → Name → Chapter 1 → Cold start after saving;
- Window zoom, F6/F7, dialogue blocking and flickering, safe exit;
- Hold platform gates before passing, do not declare support.

### X3 Windows x64 (refined on 2026-09-25)

Windows and Linux share the parts that X2 has done that have nothing to do with the backend: window handles, automatic selection of the backend to RT64, GPU completion notification, and dialogue synthesis. The window branch of `_WIN32` in `graphics.cpp` has been written, but it has not been compiled on Windows yet. The rest are mainly compilers, system services and packaging.

**Build Environment**

- Windows 10 22H2 or 11, x64.
- Tools: VS 2022 Build Tools plus “C++ Clang tools for Windows” (clang-cl), CMake ≥ 3.20, Ninja, Python 3.11 from python.org. Git sets `core.autocrlf=false` and `core.longpaths=true` to ensure byte-for-byte consistency in upstream digest checks.
- Run `tools/release/build_windows.py` in the "x64 Native Tools" command line (to be written, the structure is as follows: `build_linux.py`: Dependencies → Host → Packaging → Link Check).
- Platform-independent input copied from Mac, same as Linux: `build/recomp/cpu-bound/`, `build/recomp/audio-probe/audio.cpp`, `build/fonts/`, patched `build/recomp/upstream/`.
- **Do not cross compile on Mac. ** RT64 builds run `dxc.exe` to produce DXIL. Parallels' Windows 11 ARM virtual machine can rely on x64 simulation for compilation check, but without D3D12, actual machine acceptance cannot be done.

**Code changes** (arranged by blocking degree)

1. **CMake：**
- Release the WIN32 floodgates.
- Under clang-cl: `-include stdlib.h` is changed to `/FIstdlib.h`, `-march=x86-64-v2` is changed to `/clang:-march=x86-64-v2`.
- Added `/utf-8`, `NOMINMAX`, `_USE_MATH_DEFINES`.
- release links use `/SUBSYSTEM:WINDOWS` and `/OPT:NOICF`, the same as Zelda64Recomp.
2. **`flockfile`/`funlockfile`** (`script_trace.hpp:49,53`, `script_move_probe.hpp:34`) are replaced with portable packages, corresponding to `_lock_file` on Windows. It enters almost all host source files via `state_probe.hpp` and is the first compilation error.
3. **Wide character path:** `path::c_str()` is `wchar_t` on Windows. The screenshots involving `graphics.cpp` are written in PNG, five `native_*.cpp` and `frontend.cpp:270`'s `stbi_load`, `debug_server.cpp`, and all are changed to one `u8string()` auxiliary function.
4. **SDL:**
- RT64 links to the built-in SDL2 2.26.3 (RT64 `CMakeLists.txt:294-298`) on WIN32. The host uses `find_package(SDL2)`, and the two will conflict.
- Use the `prepare_rt64.py` patch to make RT64 also use `find_package` on WIN32. The three platforms use locked SDL3 + sdl2-compat.
5. **Dependencies:**
- SDL3, sdl2-compat, FreeType, and HarfBuzz use the same batch of source code packages and are built using CMake.
- ICU uses the MSBuild project (`source/allinone/allinone.sln`) that comes with the source code package.
- Do not introduce vcpkg to avoid the second version source.
6. **Startup:**
- When starting without parameters, first look for `rom.z64` in the user directory (`%LOCALAPPDATA%\SRW64Recomp`) and the program; if not found, use `SDL_ShowSimpleMessageBox` for explanation.
- Will be replaced by RmlUi selection page in the future, shared with Deck game mode.
- Linux now does the same thing with `marchwind64.sh`, which will take back C++ as well.
7. **Unicode path:** Add application manifest `activeCodePage=UTF-8` (supported from Windows 10 1903). `launch.cpp` The path passed through environment variables and argv will not be distorted when encountering non-ASCII user names (such as `C:\Users\太郎`).
8. **Debug interface:** ~~AF_UNIX (`debug_server.cpp`, `tools/recomp/debug/session.py:48`) was changed to loopback TCP + token~~, completed on 2026-10-06 (`debug_transport.cpp`), and the standard input and output of MCP are also fixed to UTF-8. This is an item of X0. The reason is that CPython does not have `socket.AF_UNIX` on Windows, and the actual machine acceptance of Windows depends on the debugging interface driver.
9. **Mini level:** `std::system` of `mini_stage.hpp:274` uses POSIX quotation marks and starts the child process directly instead. This is a development feature and can be turned off on Windows first.
10. **Screenshots:** Plume's D3D12 backend already supports texture → buffer copy (`plume_d3d12.cpp:2302`), so Windows' D3D12 can resume debugging screenshots before Vulkan. It is also necessary to check whether the swap chain has the COPY_SOURCE usage.

**Packaging:** `package_windows.py` zip, the content is as follows:

- Program: exe, and `SDL3.dll`, `SDL2.dll`, `freetype.dll`, `harfbuzz.dll`, ICU's DLL, `dxcompiler.dll`, `dxil.dll`;
- Resources: `fonts/`, `dialogue/`, `licenses/`.

Check the import table with `llvm-readobj --coff-imports`, only system DLLs are allowed (kernel32, user32, d3d12, dxgi, etc.). Vulkan is dynamically loaded by volk and will not appear in the import table.

**Acceptance:**

- The same process as X2;
- Run D3D12 and Vulkan each (add a `SRW64_GRAPHICS_API=d3d12|vulkan` switch for testing only);
- Non-ASCII user directory;
- 150% display zoom.

**Order:**

- W1 compilation passed: items 1–5;
- W2 can enter the game: items 6 and 7;
- W3 debugging interface and screenshots: items 8 and 10;
- W4 packaging, clean machine acceptance.

## On which machine the build steps are performed?

| Steps | Location |
| --- | --- |
| ROM layout, function scanning, CPU code generation (Python + N64Recomp) | Do it once on any machine, usually Mac. The entire `build/recomp/cpu-bound/` together with `report.json` is copied to the other machine byte by byte intact (`run_host_probe.py:194` will verify the digest). This is a ROM derivative and cannot be made public |
| RSPRecomp audio output | Same as above; `run_host_probe.py:204` needs to add the "skip regeneration" switch |
| Upstream source code pull, `prepare_rt64`/`prepare_frontend`/`build_import_spec` | Each target machine; `bootstrap.py` requires a source code only mode |
| Shader compilation, C/C++ compilation, dependencies, packaging | Per target platform; DXIL can only be generated on Windows |

There is no need to compile N64Recomp, RSPRecomp, n64sym, nor `build/recomp/venv` on the target machine.
