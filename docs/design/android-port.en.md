# Android porting plan (research)

2026-10-01. Continuation of [Three-Platform Porting Plan](three-platform-port.md). This page is the research conclusion and suggested plan, based on three parts:

- Static audit of the host code of this warehouse, the line number is based on main `c480cfe`;
- Audited the source code submitted by `config/recomp/toolchain.json` fixed RT64 (including plume submodule), N64ModernRuntime, and Zelda64Recomp, and compiled all SPIR-V shaders of RT64 with the fixed version of DXC;
- N64Recomp Android port already available in the community: I read the source code and documentation, but did not compile or run it.

**This project has not been built with NDK, nor has it been run on Android devices. ** The words marked "inference" in the article are engineering judgments, not actual measurements.

## Conclusion

- **It is feasible, most of the problems have been solved by others. ** There are at least five Android ports of N64Recomp games in the community, all of which are "builder generated code → APK sideloading → players choose their own ROM", and all use patched RT64 Vulkan for rendering. Upstream RT64, N64Recomp and Zelda64Recomp do not have official Android support, and community patches have not been integrated back into upstream.
- **Route:** SDL + RT64 Vulkan, only arm64-v8a. HD layers, dialogue synthesis and RmlUi have been plume-based and embedded with SPIR-V (three-platform plan X1), so Android and Linux share the same set of graphics code without writing a separate backend.
- **First make Android handheld, then make mobile phone touch screen. **Handheld consoles have controllers, 16:9 screens, and mostly Qualcomm Adreno GPUs. The existing Deck handle keys, key prompts and 16:9 images can be used directly, while the touch screen and mobile phone interfaces are in another stage. This is consistent with the "deck first" order.
- **Distribution:** The APK contains compiled code generated by the ROM, which is the same as the Deck package. Therefore, we only make sideload packages for our own use and are not available on Google Play.
- **Main workload (inferred):**
1. Android patches for RT64/plume/N64ModernRuntime, about ten items, and the community fork has a reference implementation;
2. The host’s application life cycle mainly means that files cannot be lost when the process is killed in the background;
3. Cross-compile and build;
4. Touch screen and mobile phone interface.

Common practices:

- The CPU code is generated from ROM on the build machine, and the APK contains compiled code without ROM data;
- All use the Android glue that comes with SDL2 2.32, and none of them use SDL3 or sdl2-compat.

**Goemon's actual performance measurement on Snapdragon 865 (Adreno 650)** (see the Android performance record of this repository):

- When the resolution is 4x and MSAA is turned off, the game runs at native 30 FPS; the resolution 8x is only 30 FPS, and the resolution 4x is 52 FPS; MSAA loses about 20%.
- Worst menu around 14 FPS. The reason is that with 20 fences per frame, the GPU frequency is scheduled to be 305–400 MHz.
- Conclusion: The Android version defaults to 4x resolution and MSAA off.

Official: Zelda64Recomp's [#45 "Android support?"](https://github.com/Mr-Wiseguy/Zelda64Recomp/issues/45) is closed as "not planned". No comments from RT64 or N64Recomp maintainers regarding Android were found.

## Upstream status (fixed commit)

### RT64 with plume

plume maintains an Android skeleton:

- `VK_USE_PLATFORM_ANDROID_KHR`;
- `RenderWindow` is defined as `ANativeWindow*`;
- Create surfaces with `vkCreateAndroidSurfaceKHR`.

This set of code comes from the initial commits of RT64 (2024-04) and plume (2025-02), and no commits have mentioned Android since. **I can’t compile it as it is, and it doesn’t draw correctly:**

| Problem | Location (upstream) | Consequences |
| --- | --- | --- |
| `static_assert(false && "Android unimplemented")` | `rt64_application_window.cpp:107,151` | Compilation failed |
| nativefiledialog unconditionally linked; its CMake treats Android as Linux | RT64 `CMakeLists.txt:74,444` | GTK3 is required during configuration, CMake fails |
| DXC and `file_to_c` selected by target platform | RT64 `CMakeLists.txt:61-65,72` | Run arm64 programs on the build machine when cross-compiling |
| The swap chain only recognizes `B8G8R8A8_UNORM` | `rt64_application.cpp:328`, `plume_vulkan.cpp:2207-2209` | The Android surface generally only provides `R8G8B8A8`, and the creation of the swap chain failed |
| The surface is only created once | plume Vulkan backend | Android will destroy `ANativeWindow` when switching to the background, and cannot be rebuilt when returning to the foreground. 2026-10-07 Fixed: `rt64_android_patches.py` allows `VulkanSwapChain::resize()` to use the current window given by the host (`graphics.cpp` is taken from SDL, if it is empty in the background, etc.) to rebuild the surface when the surface is lost or the window is changed; it will be restored by going to Home on Seeker, switching to the "File" App and then coming back. Lock screen/unlock without changing window, it was normal before |
| `preTransform` is fixed to IDENTITY | `plume_vulkan.cpp:2343` | Devices with native screen orientation will have one more system rotation per frame, about 1–3 ms, and return SUBOPTIMAL ([Android pre-rotation](https://developer.android.com/games/optimize/vulkan-prerotation)) |
| `SRC1_ALPHA` (dualSrcBlend) is used for fixed mixing, and does not check whether the device supports | `rt64_raster_shader.cpp:336-337` | **All Mali does not have this feature**, the driver still returns success, and the screen is completely white (Goemon tested on Mali-G57) |
| `preferHDR`: This is true when the local memory of the device is greater than 512 MB | `plume_vulkan.cpp:4136` | The mobile phone has unified memory and always uses the RGBA16 rendering target, which consumes more bandwidth on the block GPU (inference) |
| The idle thread dispatches computing tasks approximately every 1 ms to maintain the GPU frequency | `rt64_workload_queue.cpp:1179-1222` | Power consumption, heat generation (inference) |
| No `VkPipelineCache` and no disk cache | `plume_vulkan.cpp:1393,1652` | Recompile pipeline on every boot |

**Vulkan features that RT64 actually depends on, but does not check for:**

- **descriptor indexing:** The 8192-entry texture table uses non-uniform sample indexing, update-after-bind, partially bound, variable count and runtime array.
- **dualSrcBlend. **
- **depthClamp. **

Vulkan profiles for Android 2022, 15, and 16 do not require these three items. Only Android 17 profiles (VRA17, Vulkan 1.4) require dualSrcBlend and descriptor indexing, and only for chips shipped with Android 17.

**Unrequired:** timeline semaphore, dynamic rendering, Int64, Float16, geometry shader, sample-rate shading. The compiled SPIR-V has only Shader, Sampled1D, SampledBuffer, ImageBuffer and non-uniform index capabilities.

**Shader:** Use DXC to compile HLSL into SPIR-V during the build period and then embed it into the program. HLSL will not be compiled when running on non-Windows platforms. The only x86-specific code is hlsl++, which automatically uses NEON on arm64.

### N64ModernRuntime

- **Window handle type does not match:** `renderer_context.hpp` On Android, `WindowHandle` is defined as `SDL_Window*`, with TODO next to it, while the plume Android path requires `ANativeWindow*`.
- **Threads:** Priority is not implemented on Linux and Android (TODO).
- **Polling:** Both the graphics thread and the main loop poll every 1 ms. Linkzenic's fork changes Android's main loop interval to 16 ms.
- **Front and back:** No pause mechanism. Goemon adds `set_app_paused` and a pause gate for the VI thread.
- **Memory:** Reserve 4 GiB `PROT_NONE` first, then make 512 MiB readable and writable, there is no dead page size, and there is no problem with 16 KB pages. macOS arm64 itself is a 16 KB page.
- **ROM and archive:** `select_rom` only accepts the file system path and copies the ROM into the configuration directory; the archive is written with a temporary file and renamed. `create_directories` may throw an exception, causing Goemon to crash when the SD card is removed.
- **Error message:** The error box only hits stderr, and Android will discard stderr.

## Device threshold (inference)

| GPU | Judgment |
| --- | --- |
| Adreno 6xx and above (Snapdragon 845 and up) | First choice. dualSrcBlend support. Official driver issues encountered by Goemon: Adreno 6xx shader link failure (driver 0746), Adreno 630 null pointer in calculation dispatch of frame buffer copy. There are ways around it |
| Mali G7x and above | Requires fallback for dualSrcBlend (Goemon 1.0.3 uses single-source blend approximation). nullDescriptor may also be missing |
| PowerVR, Samsung Xclipse | No data |

Descriptor indexing and depthClamp should be checked at startup. If not satisfied, use a dialog box to explain, and avoid a blank screen or crash. After checking model by model, use gpuinfo.org to do it, **not done this time**.

## Distribution and ROM derivative code

The APK's `libmain.so` must be linked against two ROM-generated codes: `build/recomp/cpu-bound/generated/funcs_*.c` and RSPRecomp-generated `build/recomp/audio-probe/audio.cpp`. The native importer ([P1](native-rom-importer.md)) only generates text, avatars, and combat art at runtime, but cannot generate these two codes.

| Plan | Description | Conclusion |
| --- | --- | --- |
| a. Build machine-output APK and sideload | The same "self-use, do not redistribute" positioning as the Deck package | **Recommended. ** This is also a precedent for all communities |
| b. The player builds it himself | `make` on the computer, then runs the Android build, and finally `adb install` | Conflicts with the goal of P0 "Players do not install Python/compiler" |
| c. APKs without ROM-derived code, generating code on the device | Possible approach is N64Recomp's just-in-time recompiler (sljit, supports ARM64) | Not included in this plan. `generate_cpu.py` The rewrite of the generated code (about 150 `NATIVE_HOOKS` renames, overlay lookups, map width literals) and RSPRecomp audio must be changed to runtime implementation, which is a lot of work |

Two points need to be noted:

- **The project's positioning on binary distribution is inconsistent. ** `tools/release/build_release.py` Prepare the macOS package for public release on GitHub, but the Linux package says "self-use". The APK follows the maintainer's final decision, see "TBD".
- **Android developer verification. ** It will be launched in Brazil, Indonesia, Singapore, and Thailand starting from 2026-09-30, and will be promoted to the world in 2027. At that time, sideloaded APKs will need to be signed by a verified developer, otherwise they will have to go through the "advanced process" or use limited distribution to up to 20 devices ([Description](https://developer.android.com/developer-verification)). This affects sideloading patterns and requires continued attention.

The Android build machine is the same as the Linux build. It only requires four inputs. See "Which machine should the build steps be performed on" in the three-platform plan:

- `build/recomp/cpu-bound/`
- `build/recomp/audio-probe/audio.cpp`
- patched `build/recomp/upstream/`
- `build/fonts/`

## Change list

Severity: **Blocking** means it cannot be compiled or cannot be run; **Required** means it can run but is wrong or unusable on Android; **Minor** means performance, experience or only affects development functions.

### 1. Construction (blocking)

- **CMake gate:** `src/host/CMakeLists.txt:62-64` only releases Apple and Linux, Android's `CMAKE_SYSTEM_NAME` is `Android`.
- **Product form:** The game should be changed to `add_library(main SHARED …)`, add `SDL_main`, and link `android` and `log`. `srw64-frame-host` and each test program are not included in the Android build.
- **Builder Tools:** `cmake/NativeGpu.cmake`, `cmake/PixelCompositor.cmake`, `src/native/ui/CMakeLists.txt` and RT64 all select DXC and compile `file_to_c` according to the target platform. Change to:
- Press `CMAKE_HOST_SYSTEM_NAME`/`CMAKE_HOST_SYSTEM_PROCESSOR` to select DXC;
- `file_to_c` is compiled separately on the build machine and then imported. Goemon's approach is to pass `-DRT64_FILE_TO_C`.
- **Crash call stack:** `src/host/host.cpp:511-535` uses `execinfo.h` under `__linux__`, and Android also defines `__linux__`. bionic only has `backtrace` since API 33, and replacing signal handling blocks the tombstone of system debuggerd. The condition is changed to exclude `__ANDROID__`.
- **Dependencies:**
- FreeType, HarfBuzz, and ICU are changed to static linking because APK cannot accommodate shared libraries with version numbers such as `libicuuc.so.78`.
- ICU uses data filtering to retain only line breaks, bidirectional text and text system data, about 1–3 MB; full data is about 30 MB. Only `src/native/text/portable_text.cpp` uses ICU, and there is no interface using the i18n library. `cmake/PortableText.cmake` can remove `ICU::i18n`.
- HarfBuzz's pkg-config fallback will find the build machine's libraries when cross-compiling, and should be disabled on Android.
- SDL selection is shown in "TBD".
- **NDK and page size:** With NDK r28 and above, the default is 16 KB page alignment.
- **Build script:** Create a new Android build directory and `build_android.py` (to be written), with the structure as `tools/release/build_linux.py` and `tools/release/linux/Dockerfile`: NDK, JDK and Gradle are installed in the container. Input digest checks are carried over, glibc and `$ORIGIN` related checks do not apply.

### 2. Upstream patch (blocking)

Use the whitelist string replacement of `tools/recomp/toolchain/prepare_rt64.py` without forking. Each of the following items can be referenced in Goemon's fork; RT64 is licensed under the MIT license, and the source should be noted in `docs/guide/provenance.md` when adopting it.

1. **Can compile:** Remove `static_assert`; do not build nativefiledialog on Android; handle the build machine tool issues of DXC and `file_to_c` (see the previous section).
2. **Swap chain format:**
- Use `R8G8B8A8` on Android and pass the actual format to the host via the existing `GetRenderHookSwapChainTexture`.
- There are two parts of BGRA that are hard-coded in this repository: screenshot readback (`src/host/graphics.cpp:209,239`) and dialogue synthesis pipeline (`src/host/dialogue_plume.cpp:39-41`).
- Also check out RecompFrontend's interface renderer.
3. **Window and Surface:**
- `src/host/graphics.cpp` Add Android branch, get `ANativeWindow*` from SDL;
- Unify ultramodern's `WindowHandle` type;
- plume adds `setRenderWindow`, rebuilding surfaces and swap chains when coming back to the foreground (Goemon 4c087b7, c69ce04).
4. **GPU Compatible:**
- Mali's dualSrcBlend fallback;
- Feature checking and error reporting at startup;
- Turn off `preferHDR` and idle computing threads on Android;
- Protection `vkGetRefreshCycleDurationGOOGLE`;
- Handling of Adreno 6xx shader linking issues (Goemon 25fa568: spirv-opt inline, rewrite `EndianSwapUINT16`);
- "Turn off framebuffer effects" switch to bypass Adreno 630 issues.
5. **Runtime library:**
- The VI thread adds front and back pause gates and puts the rewritten version generated by `tools/recomp/toolchain/prepare_runtime_lifecycle.py`;
- `create_directories` is changed to not throwing exception;
- The error box uses `SDL_ShowSimpleMessageBox` instead;
- Main loop relaxes polling interval on Android.
6. **Do this later:** Pre-rotation, `VkPipelineCache` disk cache.

### 3. Host: entrance, path, resources (blocking)

- **User Directory:** `default_user_dir` (`src/native/app/runtime.cpp:103-123`) fell into the Linux branch on Android, requiring `HOME` or `XDG_DATA_HOME`, both of which are not available on Android. Add `Platform::Android` to use the application internal storage path provided by SDL.
- **Package resources:** `bundled_resource` reads `/proc/self/exe` (`runtime.cpp:180-194`), and gets `app_process64` on Android. So the font, dialogue text and HD cannot be found, and the sharing interface will throw "Shared UI needs a CJK font".
- **Method:** Put `fonts/`, `dialogue/` (786 txt, about 21 MB) and `licenses/` into the APK resource, press versionCode to extract to the private directory when starting for the first time, and then point the resource root directory there.
- **Why it is necessary to solve:** Dialogue loading uses `recursive_directory_iterator` to traverse the directory, and Android's `AAssetDir` cannot list subdirectories.
- **Startup entrance:**
- Now only Apple has a parameterless graphics entry (`src/host/host.cpp`). The Android portal uses SAF (`ACTION_OPEN_DOCUMENT`) to select the ROM on the Java side, copies it to `rom.z64` in the private directory, and then gives the path to C++ to assemble `Options`.
- Must be copied because `select_rom`, `sha256_file` and `fs::canonical` all have real paths.
- The logic of `srw64.sh` (finding ROM, first boot language) has also been moved into C++, which was originally planned for Windows.
- **HD Pack:**
- About 700 MB directory without APK. The host looks for it (`launch.cpp`) in the user directory `files/user/hd`, which is the same `Marchwind64-HD-<HD 版本>.zip` on the computer.
- Each HD layer uses `directory_iterator` to read the directory, so it must be an unpacked directory.
- Done (2026-10-05, `SetupActivity.importHd`): Use SAF to read the zip on the startup page, only decode the entries under `hd/` to `files/user/hd.new`, and exchange with the old directory only if `hd.json` exists. Failure or interruption will not move the installed package; display the percentage according to the compression bytes, and check the remaining space first. Three entrances: ask once after selecting a ROM for the first time; long-press the icon's static shortcut "Import HD package" (`res/xml/shortcuts.xml`, action `org.srw64.game.IMPORT_HD`); use this application to open/share the zip in a file manager or browser. The game is not imported when running (the host is not reentrant, `SRW64Activity.running`), and you are prompted to close the game first. You can still put `adb push` + `run-as` during development.
- I haven’t gone through the import process on a real device yet.
- **Logs and error reports:**
- stderr goes to logcat and writes a session log file.
- Player-oriented `std::abort()` (`graphics.cpp`, `src/host/audio.cpp`, `host.cpp`) is changed to `SDL_ShowSimpleMessageBox` first.

### 4. Life cycle and archiving (blocking, the most important)

- **Archive submission time:**
- Archives are now committed only if the host returns 0 (`src/native/app/launch.cpp:204-205`). Android often kills processes directly in the background (low memory or players cross out). The progress of the entire game will not become the "last session", and the earlier save will be quietly continued next time it is started.
- To change to an atomic checkpoint that can be submitted repeatedly: enter the background (`SDL_APP_WILLENTERBACKGROUND`), `SDL_APP_TERMINATING`, and submit once after each SRAM disk.
- This will change the P0 "Abnormal termination is not used as a recovery source" rule and requires confirmation from the maintainer.
- **Foreground and background switching:** Now the `SDL_APP_*` event is not processed at all.
- Enter background: pause guest and VI, pause audio, stop RT64 rendering, submit archive.
- Back to foreground: Rebuild surface and swap chain, then restore.
- **Risk of stuck:** `lock_ui()` of `src/native/ui/frontend.cpp` has to wait until the presentation callback clears `in_flight` before returning, and `apply_images` will also keep waiting. When the surface is lost and rendering is stalled, the main thread will be permanently blocked and Android will report ANR. Change to a time-limited wait, and proactively clear the surface when it is lost.
- **Reentrant `SDL_main`:** Neither the runtime nor the host are reentrant. When the Activity is destroyed, the process ends directly. `configChanges` is declared in the manifest and the horizontal screen is fixed.
- **More and more occupied:** Create a new session directory every time it is started, with a copy of `dialogue.json`; as well as the first 30 seconds of audio recording and the live JSON rewritten every second. Turn off recording and live JSON on Android, and clean up old sessions. `content-cache/`, `sessions/` and ROM are excluded from Android automatic backup: they are ROM derivatives and their size exceeds the backup quota.

### 5. Screen, memory and performance (must be changed)

- **Quality Default:** Now defaults to 4x MSAA plus 4x resolution. By default, Android turns off MSAA and 3–4 times the resolution, refer to Goemon’s actual measurement.
- **HD Memory:**
- All uncompressed RGBA8 with full mip chain, background max 1920×1440.
- RmlUi's image cache is never eliminated (`frontend.cpp`), and LRU must be added.
- 20.6 MB HarmonyOS SC font, each `FontSet` reads one copy, at worst five to ten copies, and needs to be changed to share a buffer.
- Release cache when `SDL_APP_LOWMEMORY` is received.
- **Diagnostic level:** When the environment variable is not set, the default is full diagnosis (regular dump of RDRAM, reading back the whole frame and encoding PNG); the full diagnosis has been deleted from the host, and the Android portal does not need to be set again.
- **Refresh Rate:** 90/120 Hz on mobile phones request 60 Hz to avoid frame time jitter.

### 6. Input and interface

**Handheld stage (required changes, small quantity):**

- The set of controllers is available as is: binding, key modification, controller → page button bridging, and PromptFont prompts.
- Intercept the Android return key and map it to B.
- Add a "handheld" judgment next to `src/host/steam_deck.hpp` for the settings page to hide the window size and full screen lines.

**Mobile phone stage (required modification, large quantity):**

- **Touch screen virtual controller:** Covers N64 keys and host keys (L2, R2, view keys, etc.). The button is sent through the input injection port (`src/host/debug_protocol.hpp`) of the debugging interface, and the page and button prompts will treat it as a handle.
- **Interface Density:**
- `sync()` of `frontend.cpp` treats a dp as an SDL point. The pixel ratio on Android is 1. On a 2400×1080 mobile phone, a 17 dp font is only about 1.5 mm high.
- To use the monitor's DPI or scaling factor instead.
- Mobile landscape screens are only about 360–430 dp high, and existing pages are designed at 540–720 dp, requiring a mobile layout or minimum physical size.
- **Safe Zone:**
- The game screen is widest to 16:9 according to `src/host/game_frame.hpp`, leaving black on both sides of the 20:9 screen and not affected by the bangs.
- The RmlUi page that covers the entire window should avoid bangs and gesture bars.
- **Touch screen details:**
- Add prompt text for touch screen;
- Add return and page turning buttons to the native page;
- Support drag and scroll;
- Solve the problem that the hover highlight does not disappear after touching;
- Merge touch move events, each event now waits for `lock_ui()` once.
- **Input method:** Use the numeric keyboard for the fund input box. `src/native/ui/text_input.cpp` is called once per frame. `SDL_SetTextInputRect` is called every time on Android. It is called only when the position changes.

### 7. Debugging interface (must be changed)

- The current AF_UNIX socket is placed in the application private directory and cannot be accessed by `adb forward`, and the path length is close to the 108-byte upper limit of `sun_path` (`src/host/debug_server.cpp`).
- Switch to the planned loopback TCP of the three-platform plan X0 and add the token, and then connect via `adb forward tcp:`. `srw64ctl` and MCP do not need to be written separately for Android.
- Actual approach (implemented): Android uses abstract sockets `@srw64-debug`, `adb forward tcp:0 localabstract:srw64-debug` to connect without tokens. Desktop three platforms 2026-10-06 changed to loopback TCP plus token, see [Debugging interface · Connection method](../guide/debug-interface.md#连接方式).
- The release build must be able to remove the debugging interface during compilation.

### Already portable, no need to change

- **Graphics:** HD layers, dialogue compositing, RmlUi all go plume and embed SPIR-V. `native_gpu`'s ring constant buffer, 16-byte push constant, and format-specific pipeline are all suitable for mobile GPUs.
- **ARM Correctness:** Weak memory ordering, 16 KB pages, and little-endian assumptions, all verified on macOS arm64.
- **Text and Art:** The text stack is all C interface, and fonts are loaded from memory. The aspect ratio is adaptive from 4:3 to 16:9.
- **POSIX part of application layer:** `flock`, atomic renaming and `std::filesystem` all work on bionic.
- **Debugging tools:** Various QA and probe tools are enabled by environment variables and do not take effect by default.
